## Why <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span>?

</summary>

The honest answer: the obvious name, [`gitui`](https://github.com/extrawurst/gitui), was already taken. And since I'm French, and we obviously love baguettes, I went with the next best thing: stitch a `oui` to the end of `git`. Voilà, <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span>. A small bilingual joke that doubles as a tagline, the project says **yes** to a fuller TUI workflow.

<summary>

## Can <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> replace lazygit / gitui?

</summary>

Different focus. lazygit and gitui are full git operations toolkits, every command surface is interactive. <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> starts from "I want to read history and review changes" and adds the operations that fit naturally on top of that: stage, commit, rebase, resolve conflicts, review PRs.

Use <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> if your daily flow is **read-heavy** with frequent reviews + some editing. Use lazygit/gitui if you want to drive every git command through the TUI.

</details>

<summary>

## Why is Alt+letter not firing on my system?

</summary>

<span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> pushes the Kitty keyboard protocol's `DISAMBIGUATE_ESCAPE_CODES` flag at startup, that makes `Alt+letter` arrive as a single KeyEvent on supporting terminals (Kitty, Ghostty, WezTerm, foot, Konsole 22.04+, …). Older terminals treat Alt as a meta-prefix and send `Esc` followed by the letter; usually crossterm combines them, but if the bytes drift apart you end up firing `Cancel` (Esc) before the letter arrives.

If your terminal doesn't speak the protocol, switch to `Ctrl+...` for your custom bindings, see [Custom keybindings](../keybindings/custom/).

</details>

<details class="faq-item">
<summary>

## My Help page still shows the default after rebinding a key

</summary>

Help is computed from your live config at render time. If the displayed key is wrong:

1. Check your config validated, <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> prints a styled diagnostic at startup if there's an error.
2. Make sure you're on the right config file (`GITOUI_CONFIG_FILE` env variable might be overriding the default location).
3. Some glyphs in the Help page are intentionally symbolic, `Esc`, `↑↓`, `Enter`, `Tab`, `Space`, `#`. These don't follow rebinds (only the action's *behaviour* moves, not the label).

</details>

## Where do my settings live?

</summary>

| Path                                    | What                            |
|-----------------------------------------|---------------------------------|
| `~/.config/gitoui/config.toml`          | Main config.                    |
| `~/.config/gitoui/themes/<name>.toml`   | Custom theme files.             |
| `~/.config/gitoui/github_token.toml`    | OAuth token (mode `0600`).      |
| `~/.cache/gitoui/avatars/`              | Avatar PNG cache.               |
| `~/.cache/gitoui/<repo-hash>/commits.bin` | Commit history cache. Speeds up subsequent launches by avoiding a full `git log` walk. Invalidated automatically when HEAD moves or sort order changes. Clear manually with `gitoui -C`. |
| `~/.config/gitoui/logs/`               | Daily-rotating debug log files.  |

On Windows, settings, themes, the token and logs are under `%APPDATA%\gitoui` and the caches under `%LOCALAPPDATA%\gitoui`.

Set `GITOUI_CONFIG_FILE` to point at a different file. The themes folder and cache always live next to the config.

</details>

## Can I disable the image protocol?

</summary>

`gitoui --graph-renderer ascii` uses Unicode box-drawing characters for the commit graph and skips avatar rendering. The result looks like a slightly fancier `git log --graph` and works in any terminal.

</details>

## Does <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> run on Windows?

</summary>

Yes, as an experimental target. Install it from PowerShell (`irm https://gitoui.nayji7.dev/install.ps1 | iex`) and run it in **Windows Terminal**, from PowerShell or cmd. There the commit graph and avatars are real images (Sixel, detected at startup, Windows Terminal 1.22 or later). Settings live in `%APPDATA%\gitoui`. Details in the [Windows notes](/getting-started/compatibility/#windows).

</details>

<details class="faq-item">
<summary>

## Nothing shows up (or it exits with a message) in Git Bash

</summary>

Git Bash's own window (mintty) does not provide the Windows console that <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> reads the keyboard from, so it stops with a message instead of drawing a screen that never answers. Open Git Bash as a Windows Terminal profile, or use PowerShell or cmd. `winpty gitoui` is the usual workaround for Windows programs in mintty; it has not been tested with <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> yet.

</details>

<details class="faq-item">
<summary>

## The images are misaligned after I zoomed the font in Windows Terminal

</summary>

<span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> reads the size of a character cell once, at startup, and fits every image to it. Windows Terminal keeps reporting the old size after a zoom (`Ctrl` + wheel), so the images stop lining up with the rows. Quit and start <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> again at the new size, or use `--graph-renderer ascii`.

</details>

<details class="faq-item">
<summary>

## How do I copy text from the screen?

</summary>

Hold `Ctrl` and drag over the text, in any view. It is copied as soon as you release the button, and the footer says `Copied N chars to clipboard`. A plain click or drag keeps doing what the view does with it, and `Shift` + drag is your terminal's own selection, which you copy with the terminal's copy shortcut (in Windows Terminal that is whatever your settings bind, often `Ctrl+C` while a selection exists).

</details>

<details class="faq-item">
<summary>

## My terminal scrambles the graph after I exit

</summary>

<span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> pops the Kitty keyboard protocol on exit, but **inline image placements** (Kitty / iTerm2) sometimes linger if you exit via a crash or `SIGKILL`. Press `Ctrl+L` in your shell to clear the screen, that flushes the stale placements.

</details>

<details class="faq-item">
<summary>

## Does <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> send any data to a server?

</summary>

There is no telemetry, no analytics and no crash reporting. These are the network requests it makes:

- **Update check (on by default).** At most once every 24 hours, and only when started in an interactive terminal, gitoui sends `GET https://crates.io/api/v1/crates/gitoui` to read the latest version. Nothing else is sent. If a newer version exists and you installed with the curl script, it also checks with a `HEAD` request that the matching archive is published on GitHub Releases. Nothing is installed without your answer at the prompt, and Homebrew installs are never prompted. Turn it off with `--no-update-check` or `check_updates = false` under `[core.option]` (answering `N` at the prompt sets it for you). `gitoui --update` checks on demand.
- **GitHub, only after you sign in.** Sign-in uses GitHub's device flow. Once signed in, gitoui calls `api.github.com` for the repository's GitHub remote: when you open the Pull Requests or Issues views, and to show author avatars in the commit list, blame, file history and commit details (it asks GitHub which account authored a commit, then downloads that avatar). Avatars are cached on disk. Set `github_avatars = false` under `[core.option]` to stop avatar requests; the ASCII renderer never loads them.
- **git itself.** Fetch, pull and push run the `git` CLI against your remotes. gitoui also runs `git fetch --all` in the background after a commit, stash, push or tag made from the UI, and fetches a pull request's commit from GitHub when you open one that isn't available locally.
- **install.sh (not the binary).** After a real install or update, the script sends one `GET` to an install counter that only stores a running total. Set `GITOUI_NO_TRACK=1` to skip it.

</details>

<details class="faq-item">
<summary>

## Is <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> stable enough to use on real repos?

</summary>

It's daily-driven on the <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> repo itself and on a few sandboxes. Pre-v1.0 means the config schema and some keybinds may still shift, your `.toml` config might need touches when you upgrade. The on-disk git operations are all plain `git` CLI calls, no libgit2, so worst-case <span class="gitoui-wordmark"><span class="git-part">git</span><span class="oui-part">oui</span></span> never corrupts state; it just produces an error you'd see from `git` directly.

</details>
