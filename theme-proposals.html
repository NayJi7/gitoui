gitui — Propositions de thèmes

Renommer « Syntax Theme » → « Thème » + appliquer à toute l'interface

Recommandé Thèmes UI complets — Créer 5-6 thèmes entièrement définis, chacun avec sa palette complète (fond, texte, sélection, refs, diff, header) et un thème syntaxe correspondant embarqué. L'utilisateur choisit un seul Thème et tout l'interface change. La config syntax_theme existante peut rester pour un override manuel.

Avantages : Cohérence parfaite, contrôle total, visuels de qualité.  ·  Inconvénients : Nécessite de définir chaque palette à la main (~6 thèmes).

Alternative Dériver l'UI depuis le thème syntaxe — Extraire bg/fg/accent du thème .tmTheme sélectionné et en déduire les couleurs de toute l'interface (sélection = bg+20% luminosité, texte secondaire = fg@70%, etc.).

Avantages : Cohérent par construction, un seul concept "thème".  ·  Inconvénients : Les thèmes syntaxe ont une palette limitée — certains résultats peuvent être visuellement pauvres. Le mapping bg→UI est fragile (ex: Solarized Light donnerait un fond blanc pour toute l'interface).
Thème syntaxe
⚠️ Limite principale : Les thèmes syntaxe (.tmTheme) définissent des couleurs pour les tokens de code, pas pour les éléments d'interface. Le mapping bg→fond global et accent→refs donne des résultats approximatifs. Exemple : InspiredGitHub a un fond blanc — toute l'UI deviendrait blanche. L'approche B donne un bien meilleur résultat.
Alternative Hybride — Des thèmes UI complets (comme B), mais le thème syntaxe reste un paramètre séparable. Le thème UI définit un thème syntaxe par défaut cohérent, mais l'utilisateur peut l'overrider indépendamment.

Exemple : Thème UI = Dracula → syntaxe = Dracula par défaut, mais l'utilisateur peut changer la syntaxe en Monokai sans changer l'UI.

Avantages : Flexibilité maximale. Bonne option si l'utilisateur a déjà configuré son thème syntaxe favori et veut juste changer l'UI.  ·  Inconvénients : Deux niveaux de config. Plus complexe à implémenter et à documenter. Dans la pratique, les deux niveaux peuvent diverger et l'interface peut sembler incohérente. L'approche B (un seul "Thème") est plus simple et couvre 95% des cas.
Structure de config envisagée :
[core.option]
theme = "Dracula"  ← nouveau, remplace syntax_theme
syntax_theme_override = "Monokai"  ← optionnel, override la syntaxe
